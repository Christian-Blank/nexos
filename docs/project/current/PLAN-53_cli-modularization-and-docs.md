# PLAN‑53 — CLI modularization & discoverability

> Mission alignment: reduce entropy, keep speed safe, make the CLI self‑describing for both humans and LLMs, and co‑locate tests for atomic ownership.

## Problems we’re solving

- Monoliths: single Rust files creeping to ~3000 lines → unreadable, unreviewable.
- Discoverability: it’s hard to see available commands in code or in generated docs.
- Drift: CLI docs not standardized → they drift from code.
- LLM friction: even when “docs as code” exists, there’s no deterministic, sliceable structure for agents/humans.
- Tests not co‑located: most tests live only in `nexoscli-bin/tests/` → violates atomic plugin principle.

## Outcomes (acceptance criteria)

1. Modular code: no plugin file > 800 LOC; dev plugin subcommands are in modules (`plugins/dev/src/cmd_*`).
2. Single source of truth for args: each command’s args struct derives both `clap::Args` and `schemars::JsonSchema`, eliminating duplication.
3. Deterministic docs:
   - `nexoscli dev docs commands --out docs/CLI_REFERENCE.md` emits a full command tree from live code.
   - Each plugin README has an AUTO (id=commands) block regenerated by `dev docs commands`.
   - CI fails on docs drift (generated vs. committed).
4. Agent‑grade catalog: `docs/catalog/commands.json` (machine‑readable command tree + JSON Schemas).
5. Co‑located tests: each plugin has a `tests/` dir with at least one integration/unit test; E2E stays in `nexoscli-bin/tests/`.
6. Repo gates:
   - `nexoscli dev plugins check` warns if any `src/*.rs` > 1000 LOC; fails at > 2000.
   - `nexoscli dev repo check` warns if a plugin lacks `tests/` or a README commands block.
7. Zero‑knowledge onboarding: a newcomer (or LLM) can start at root README → plugins → command → example usage in ≤ 4 clicks.

## Non‑goals

- Rewriting every test today (we co‑locate minimal tests per plugin; keep E2E as‑is).
- Changing user‑visible CLI behavior beyond re‑organizing code and improving docs.
- Introducing a fully new DSL for command definitions.

## Design (selected option)

Option A — Unified struct derives (Clap + Schemars) + modular files — SELECTED

- Define each command’s Args once:
  ```rust
  #[derive(Debug, Clone, Serialize, Deserialize, schemars::JsonSchema, clap::Args)]
  struct DevInitArgs {
      #[arg(long = "dry-run")] dry_run: bool,
      #[arg(long)] yes: bool,
      #[arg(long = "with-config")] with_config: bool,
  }
  ```

- Split dev plugin into modules:

```
plugins/dev/src/
├─ lib.rs                # thin router
├─ cmd_init.rs
├─ cmd_plugin_new.rs
├─ cmd_plugins_check.rs
├─ cmd_repo.rs
├─ cmd_log.rs
├─ cmd_doctor.rs
├─ cmd_telemetry.rs
├─ cmd_docs.rs
├─ cmd_schemas.rs
└─ cmd_plans.rs
```

- Add introspection/export:
  - `nexoscli dev docs commands` walks the clap Command tree to produce:
    - `docs/CLI_REFERENCE.md` (human)
    - `docs/catalog/commands.json` (machine)
  - Every plugin README contains:
    ```
    <!-- BEGIN: AUTO (id=commands) -->
    _generated by `nexoscli dev docs commands`_
    <!-- END: AUTO -->
    ```
- Tests move per plugin (unit/integration), with a shared testsupport module/crate for common helpers.

Why this beats alternatives
- Option B (Declarative YAML spec → generate clap + docs): adds a second source of truth; risky drift; harder Rust ergonomics.
- Option C (Stay with builder API, add exporters): helps docs but not file size/modularity/maintainability.

⸻

## Work plan (phased, safe-at-speed)

Phase 1 — Dev plugin pilot (code split + docs/export)
- Create modules `cmd_*` and move each subcommand’s handler + args there.
- Convert select commands to derive Args + JsonSchema (start with: init, plugins check, repo check, docs build).
- Add `nexoscli dev docs commands`:
  - exports full command tree (plugin → subcommands → flags, defaults) to `docs/catalog/commands.json`
  - writes/refreshes:
    - `docs/CLI_REFERENCE.md` (includes `nexoscli --help` and per-plugin sections)
    - plugin README AUTO (id=commands) blocks
- Update CI:
  - Run `nexoscli dev docs commands` and fail on diff.
  - Run `nexoscli dev plugins check` with line-count and README checks.

Phase 2 — Co‑locate minimal tests per plugin
- Add `plugins/<name>/tests/` with 1–2 focused tests invoking the plugin module (no full binary).
- Extract `nexoscli-testsupport` (workspace dev‑dependency) for common helpers (temp dirs, run context, fixtures).
- Keep binary E2E tests in `nexoscli-bin/tests/` (no mass move).

Phase 3 — Roll across plugins + tighten gates
- Convert remaining commands to derive Args + JsonSchema.
- Enforce gates in `dev doctor --ci` profile v0:
  - docs drift
  - per-plugin tests present
  - no `src/*.rs` > 2000 LOC
- Add README AUTO (id=tools) blocks (from tools export) under each plugin.

## Risks & mitigations
- Risk: derive migration breaks clap behavior  
  Mitigation: migrate command‑by‑command; keep the builder for edge cases initially.
- Risk: doc generator diverges from runtime help  
  Mitigation: generator reads the live clap tree; drift checks in CI.
- Risk: test duplication/confusion between plugin vs. bin  
  Mitigation: document test layering in root README; keep E2E only in bin.

⸻

## Rollback
- Revert module split PR; keep the doc generator (it’s read‑only). No on‑disk format change; no user‑visible CLI change required.

## Why this plan (the “blue‑team / red‑team” in brief)

### Blue‑team (pro):
- Single truth for args via `#[derive(Args, JsonSchema)]` eliminates drift between CLI, docs, and tool specs.
- Deterministic docs from the live clap tree gives both humans and LLMs a stable, queryable index.
- Modularization improves reviewability, ownership, and makes command discoverability obvious by file name.
- Co‑located tests align with your monorepo/DDD model: atomic, recursive, and scalable.

### Red‑team (con):
- Derive‑based args can be limiting for some advanced clap cases (exotics).  
  Answer: keep the builder for those few cases; everything else moves to derive.
- Another generator adds CI cost and complexity.  
  Answer: generation is cheap text/JSON; we already generate rules and schemas—this aligns with that pattern.

## Implementation notes (concrete, no guesswork)

### 1) File layout for dev plugin

```
plugins/dev/src/
lib.rs            # thin: call into submodules
cmd_init.rs       # Args + run()
cmd_repo.rs
cmd_plugins_check.rs
cmd_docs.rs
cmd_log.rs
cmd_doctor.rs
cmd_telemetry.rs
cmd_schemas.rs
cmd_plans.rs
```

Pattern per module

```rust
// plugins/dev/src/cmd_init.rs
use clap::Args;
use schemars::JsonSchema;
use serde::{Serialize, Deserialize};
use nexoscli_core::plugin::{CommandContext};
use nexoscli_core::Result;

#[derive(Debug, Clone, Serialize, Deserialize, JsonSchema, Args)]
pub struct DevInitArgs {
  #[arg(long = "dry-run")] pub dry_run: bool,
  #[arg(long)] pub yes: bool,
  #[arg(long = "with-config")] pub with_config: bool,
}

pub fn subcommand() -> clap::Command {
  use clap::{ArgAction, Command};
  Command::new("init")
    .about("Initialize .nexoscli/ (Plan/Apply, idempotent)")
    .arg(clap::Arg::new("dry-run").long("dry-run").action(ArgAction::SetTrue))
    .arg(clap::Arg::new("yes").long("yes").action(ArgAction::SetTrue))
    .arg(clap::Arg::new("with-config").long("with-config").action(ArgAction::SetTrue))
}

pub fn run(m: &clap::ArgMatches, ctx: &CommandContext) -> Result<i32> {
  // parse DevInitArgs from ArgMatches or use your existing accessors
  // then perform the existing logic (moved here from lib.rs)
  // return ctx.ok/ctx.err as before
  // …
  Ok(ctx.ok("dev","init", &serde_json::json!({"migrated":true})))
}
```

Why both derive + builder?  
Derive gives us schema & clap metadata for free; the small `subcommand()` wrapper preserves exact UI semantics while we transition.

### 2) Export the command tree (machine + human)
- In `nexoscli-bin/src/main.rs`, after building the clap root Command tree, add an internal call that walks Command:
  - name, about, long_about, subcommands, each Arg (long, short, help, required, default, value_parser kind)
- `nexoscli dev docs commands`:
  - Writes `docs/catalog/commands.json` (sorted keys, stable order).
  - Builds `docs/CLI_REFERENCE.md` with:
    - Top‑level help
    - Per‑plugin sections
    - Per‑command flags table + Examples (auto from tests/fixtures where available, else from hardcoded example in module).
  - When `--apply-readmes` is set, it updates each plugin README’s `<!-- BEGIN: AUTO (id=commands) -->` block.

### 3) README auto‑blocks (per plugin)

Add this block to each plugin README once:

```
## Commands

<!-- BEGIN: AUTO (id=commands) -->
_Generated by `nexoscli dev docs commands`._
<!-- END: AUTO -->

## Tool specs (for agents)

<!-- BEGIN: AUTO (id=tools) -->
_Generated by `nexoscli tools export`._
<!-- END: AUTO -->
```

Hook these into dev docs build or the new `dev docs commands` so they get refreshed deterministically.

### 4) Co‑located tests
- New dev‑dependency crate: `nexoscli-testsupport` (workspace member) with:
  - temp dir helpers
  - fake `CommandContext` builder
  - JSON assertion helpers
- In each plugin:

```
plugins/<name>/tests/
  smoke.rs           # at least one
  <feature>.rs       # optional additional
```

- Keep E2E (binary‑level) in `nexoscli-bin/tests/`.

### 5) CI & repo checks
- Extend `dev plugins check`:
  - count LOC per `src/*.rs` → warn at 1000, error at 2000
  - detect `tests/` folder existence
- Extend `dev repo check` (or `dev doctor --ci` v0 profile):
  - run `nexoscli dev docs commands` & `nexoscli dev docs build`, then fail if diffs
  - verify plugin README has updated AUTO (id=commands) (unless allow‑list)
